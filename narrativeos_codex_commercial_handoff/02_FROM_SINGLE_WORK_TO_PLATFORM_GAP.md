# 02. 从单一作品到通用平台：差距与改造原则

## 一、单一作品实现常见症状

现有 Alpha 最容易隐藏在代码里的问题不是“bug”，而是 **叙事资产与运行逻辑耦合**。

典型症状：

1. 角色名、关系、主题、结局形态直接写在 runtime 默认值里。
2. 事件库只适用于一个世界，换题材就失效。
3. scene intent 实际上绑定某个作品的戏剧节奏。
4. renderer 偏向某个文风或单一人物关系。
5. 前端只考虑一个读者路径，不考虑 world shelf / library / entitlements。

## 二、平台化改造的总原则

### 原则 1：引擎只处理“通用叙事语义”
引擎只理解：
- 世界规则
- 角色原型与实例
- 场景蓝图
- 因果种子
- 关系债
- 路线、章节、选择、结局门控

引擎不应该理解：
- 某个具体人物名
- 某个 IP 专属设定
- 某个题材专属俗成桥段

### 原则 2：题材差异要由 World Pack 提供
题材差异通过资产层表达，而不是代码 if/else 表达。

### 原则 3：商业化能力要成为一等公民
任何对外可卖的内容，都必须能回答：
- 这是谁的 world pack
- 当前版本号是什么
- 内容风险等级是什么
- 使用了多少生成额度
- 是否通过审核
- 哪些用户有权访问

## 三、要抽离成“平台级标准”的 8 件事

1. **World Pack 标准**
   - 世界观、角色、场景蓝图、风格、策略、规则、风险标签
2. **Narrative Runtime 标准**
   - 会话、章节、候选路线、评分、渲染、审核
3. **作者工具标准**
   - author brief、world composer、route simulator、quality dashboard
4. **发布标准**
   - validate -> simulate -> review -> publish -> archive
5. **权限与计费标准**
   - entitlements、credits、metering、usage records
6. **审核标准**
   - 风险等级、规则命中、人工复核、版本留痕
7. **评测标准**
   - 质量、稳定性、多样性、成本、留存 proxy
8. **数据闭环标准**
   - 在线事件、章节完成、选择分布、付费转化、世界热度

## 四、必须避免的错误

- 用“多加几个世界示例”冒充平台化
- 把作者工具做成 prompt 文本框
- 先上付费，再补审核和 metering
- 把 world-specific hacks 永久放进 runtime
- 用一个模型承担规划、模拟、渲染、批评、审核全部职责

## 五、目标状态

当平台化完成时，NarrativeOS 应该满足：

- 新作者无需改代码即可导入新 world pack
- 新题材无需改 runtime 逻辑即可运行
- 新世界上线前有统一验证和评测流程
- 任意章节都能追踪成本、权限、版本、审核记录
- Reader / Author / Ops 三类产品都共享同一套核心语义
